# EvidenceAgent — 项目复盘与技术总结

## 1. 项目概述

本项目围绕企业制度知识问答场景，设计并实现了一个基于真实 LLM Tool Calling 的 ReAct Agent，支持文档自主检索、原文查证、制度冲突识别、结构化事实校验、异常恢复及完整执行追踪。

与传统单轮 RAG 问答不同，EvidenceAgent 不仅关注答案生成，还重点解决三个工程问题：

1. **决策自主性**：模型能够根据工具实际返回结果，自主选择继续检索、读取文档、修正答案或结束任务。
2. **回答可信性**：通过确定性校验约束引用来源、事实准确性、制度适用范围及问题覆盖，降低无依据回答的风险。
3. **执行可验证性**：通过 Mock/Live 分层测试、语料变异、故障注入和结构化 Trace，验证 Agent 的实际行为，而非仅检查最终输出。

项目采用 AI 辅助开发模式。本人主要负责需求定义、架构方案评审、关键技术取舍、验收标准制定及问题修复方向确认；Codex 辅助完成代码实现、测试构建和迭代修复。具体分工见 `docs/04-ai-usage.md`。

### 实际验证结果

| 验证指标 | 实际结果 |
|---|---|
| 离线自动化测试 | 142 项通过 |
| 真实模型 Live 测试 | 14 项通过 |
| 首次全量测试 | 122 passed / 5 failed |
| 修复后测试 | 156 项通过（142 Offline + 14 Live） |
| 真实 Live Trace | 15 条 |
| Live 模型请求 | 57 次 |
| 动态决策验证 | 正常检索与故障检索产生不同后续动作 |
| 主要测试模型 | DeepSeek Flash（非思考模式） |

这些结果来自实际运行记录，反映指定测试环境与测试批次的执行情况。所有关键结论均可通过 `docs/03-evaluation.md` 中引用的测试报告和 Trace 核验。

## 2. 核心工程挑战与技术取舍

### 2.1 挑战一：如何平衡 Agent 自主决策与系统可靠性？

**问题分析**

Agent 的核心价值是动态决策，但完全依赖 LLM 处理工具调用、业务冲突和事实验证，容易产生不受控行为。

如果将查询改写、冲突处理和工具选择全部写成固定条件分支，又会退化为传统 Workflow，无法体现真实的 Agent 决策能力。

**技术方案**

采用“LLM 自主决策 + 确定性运行时保护”的分层架构：

- **LLM 决策层**：根据用户问题和工具 observation 自主决定下一步动作。
- **工具执行层**：负责参数校验、工具调用、异常捕获与结果返回。
- **证据校验层**：检查引用真实性、规则适用范围、事实一致性及制度冲突。
- **运行时保护层**：限制执行预算、处理协议异常、记录真实 Trace。

其中最重要的原则是：

**校验器可以拒绝不可信的结果并指出缺口，但不能代替模型作出下一步业务决策。**

例如，模型仅读取 D01 后尝试提交报销期限，如果元数据表明还存在潜在冲突的 D02，校验器将返回未解决冲突及相关条款 ID，而不是直接替模型读取 D02 或选择最终制度。

**实际验证**

动态对照实验采用相同问题与模型，分别提供正常检索结果和注入故障的检索结果：

- 正常分支：模型观察到检索成功后，下一步选择 `read_doc(D03)`。
- 故障分支：模型观察到 `INJECTED_FAILURE` 后，下一步选择重新调用 `search_docs`。

两条路径均来自真实模型执行，而不是预设 Mock 响应，满足项目对动态工具决策的核心要求。

**设计收获**

Agent 的自主性与系统的可控性不是对立关系。将非确定性决策交给 LLM，将确定性校验交给代码，可以在保留 Agent 灵活性的同时，提高执行结果的可靠性与可解释性。

### 2.2 挑战二：如何确保答案不仅有引用，而且真正回答用户问题？

**问题分析**

传统 RAG 系统经常以引用是否存在作为可信性判断依据，但“引用真实”不等于“答案正确”。

例如，用户询问试用期员工的远程办公制度，模型可能引用一份真实的正式员工制度。虽然引用有效，答案却不适用于用户。

另外，模型可能在正确引用后添加原文没有支持的推断性内容。

**技术方案**

采用受控 Claims 机制，并引入多层确定性校验：

1. **引用校验**：引用必须来自本次执行中成功读取的原始文档。
2. **事实校验**：核对结构化规则的数值、单位、约束类型和原文依据。
3. **范围校验**：区分正式员工、试用期员工及其他业务条件。
4. **问题覆盖校验**：验证最终 Claims 是否覆盖用户询问的主题和必要条件。
5. **冲突完整性校验**：防止模型忽略仍然有效的潜在冲突制度。

在规则建模中，使用 `MAX`、`MIN`、`EXACT`、`DEADLINE` 等约束语义，避免把“最多两天”错误解释为“必须两天”。

最终答案由通过校验的 Claims 生成，不直接采用未经验证的自由文本。

**实际验证**

在 C05 上下文追问测试中，模型首次提交了不适用于试用期员工的事实声明。

校验器正确拒绝该声明，模型观察到拒绝反馈后，在下一轮移除错误内容并重新提交，最终获得有效结果。

这说明校验机制不仅具备错误拦截能力，还支持模型根据反馈进行修正。

**设计收获**

可信知识问答需要同时满足四个条件：

**证据真实、事实正确、适用范围匹配、用户问题得到充分回答。**

单纯提高检索相似度或增加文档引用数量，并不能替代这些校验。

### 2.3 挑战三：如何保证复杂工具调用的协议完整性？

**问题分析**

真实模型可能一次返回多个工具调用，也可能产生无效参数、混合终止动作或重复调用。

如果只处理部分工具调用，容易造成消息历史不完整；如果忽略执行预算，则可能出现无限调用或超额执行。

**技术方案**

执行器采用严格的工具调用协议：

- 使用实际 `tool_call_id` 对应每一次工具 observation。
- 对超预算动作返回明确的 `BUDGET_EXCEEDED`，不执行实际业务逻辑。
- 对混合批次中的 `submit_answer` 进行独立校验。
- 将模型调用、工具尝试、实际执行和跳过操作分别计数。
- 对非法参数和校验失败返回结构化错误。
- 设置最大模型调用轮次和工具调用次数，避免无限循环。

同时引入无进展检测，识别连续重复调用且没有新增证据的情况，避免模型反复消耗资源。

**设计收获**

Agent 执行器不仅是工具函数的分发器，还承担协议一致性、错误隔离、执行预算和状态管理职责。可靠的运行时保护是 Agent 能够稳定工作的基础。

## 3. 最重要的一次工程迭代：真实 Live 失败驱动修复

这是整个项目中最具代表性的一次问题解决过程。

### 3.1 真实模型测试暴露了什么？

首次完整 Live 验证结果为：

**122 passed / 5 failed。**

通过检查真实 Trace，发现问题并非全部来自检索失败，而是模型输出、参数 Schema 和校验器之间存在契约不一致。

| 失败场景 | 根本原因 |
|---|---|
| C04 相似表述 | 正式员工重复进入 scope 和 conditions，修正又被错误拦截 |
| C05 上下文追问 | 模型推断条件被误当成不可修改的用户约束 |
| T04 冲突消失 | 错误的范围解释和起算事件导致提交无法修正 |
| T06 一次性工具故障 | “每周”被误填为 reference_event，修正机制无法恢复 |
| 动态决策对照 | 周期别名未规范化，测试错误地比较了未实际执行的动作 |

还发现 C06B 存在测试假通过：系统返回了预期失败状态，但实际没有执行目标故障工具。

这一问题说明，**只检查最终状态不足以证明 Agent 完成了预期执行路径。**

### 3.2 如何确定修复方向？

本轮没有选择简单增加模型调用次数、降低校验要求或修改测试预期，而是围绕真实 Trace 中的共性问题，明确四项修复方向。

**第一，建立字段语义规范化。**

统一处理合法的周期别名，明确区分员工范围、附加业务条件、周期和参考事件，避免同一信息出现在不恰当的字段中。

**第二，区分用户硬约束与模型推断。**

用户明确提出的约束必须保留，但模型自行添加且缺乏依据的错误解释应允许修正。

避免将模型首次提交的错误字段永久锁定，形成无法恢复的校验循环。

**第三，改进校验反馈。**

将笼统的提交失败改为具体字段级错误反馈，明确错误类型、字段语义和修正边界，使模型能够根据 observation 采取有效修正动作。

**第四，强化实际执行路径验收。**

故障测试必须验证故障确实发生；动态对照必须比较成功执行的工具调用及模型在后续轮次采取的动作。

仅有正确最终状态，不能视为执行行为得到验证。

上述修复原则经过人工评审确认，由 Codex 辅助完成具体实现与回归测试。

### 3.3 如何证明修复有效？

本轮采取“失败样例复现 → 实现修改 → 离线回归 → 真实模型验证”的方式。

具体结果如下：

- 新增的 10 项针对性回归测试在旧实现上全部失败，能够有效暴露原始缺陷。
- 修复后完整离线测试为 **142 passed**。
- 随后执行 14 项真实 Live 测试，结果为 **14 passed**。
- C04、C05、T04 和 T06 均完成预期业务流程。
- C05 保留了错误声明被拒绝后，模型重新提交成功的真实记录。
- C06B 实际观察到四次检索故障，最终明确返回 `FAILED`。
- 动态决策对照观察到检索成功后的文档读取，以及检索失败后的重新检索。

在证据管理方面，旧版 64 个 Live 文件的 SHA256 校验结果保持一致，修复过程没有覆盖历史失败记录。

### 3.4 这次迭代带来的关键认识

**Agent 的失败不一定意味着模型缺乏推理能力，也可能意味着系统没有为模型提供合理的交互契约和错误恢复机制。**

例如，当模型试图修正自己的错误解释时，如果校验器把错误解释当作不可改变的用户要求，即使模型已经识别问题，也无法完成修复。

因此，Agent 调试不能只依赖最终答案，而要检查：

- 模型选择了什么动作；
- 工具是否实际执行；
- 工具返回了什么 observation；
- 校验器为何拒绝提交；
- 失败反馈是否允许合理修正；
- 下一轮模型是否真正改变行为。

这是一种从结果导向转向执行过程与证据导向的工程思路。

## 4. 测试方法与质量保障的反思

### 4.1 Mock 测试与 Live 测试必须分层

离线测试可以稳定验证执行器、工具和确定性校验逻辑，但无法完整模拟真实模型的字段表达和工具选择行为。

首次 Live 测试出现的 scope/conditions 混淆、周期别名和错误修正死锁，正是 Mock 夹具未能覆盖的情况。

因此，本项目明确划分：

- **单元测试**：验证检索、规则、引用和执行边界。
- **Mock 测试**：验证工具协议与确定性处理流程。
- **Live 测试**：验证真实模型的动作选择、错误修正与终止行为。
- **语料变异测试**：验证答案是否随当前证据变化。
- **动态决策对照**：验证不同 observation 是否影响后续动作。

### 4.2 测试应该验证行为，而不仅是结果

C06B 假通过说明，仅检查最终 `FAILED` 或 `INCOMPLETE` 状态是不充分的。

因此，验收标准不仅关注结果，还关注必要的执行前提：

- 工具故障测试应实际触发故障。
- 冲突测试应读取并引用必要的冲突证据。
- 动态决策测试应具有真实工具 observation 及后续模型动作。
- 资料不足测试不得虚构企业事实。
- 事实核验失败后应保留拒绝与修正记录。

### 4.3 保留失败证据比只展示成功案例更有价值

本项目将 Trace、测试结果、运行配置摘要与文件哈希关联保存，并保留修复前的失败记录。

这种方式能够支持问题复现、根因分析和修复效果对照，也能防止通过筛选成功样本夸大实际效果。

本轮 Live 测试全部通过，证明系统在指定场景中具备预期行为；但模型输出具有不确定性，单次全通过并不意味着所有后续运行都具有相同结果。

## 5. 主动学习与技术能力提升

本项目让我对 Agent 开发形成了三个更加明确的认识。

### 5.1 从关注模型能力转向关注完整系统契约

最初容易把 Agent 能否完成任务理解为模型是否足够智能。

实际测试表明，模型能力只是其中一部分。工具参数定义、字段语义、证据结构、错误反馈和终止条件，同样会直接影响 Agent 的表现。

因此，设计 Agent 时应将 Prompt、工具 Schema、运行时校验和业务验收视为一套相互配合的系统契约。

### 5.2 从结果验证转向过程验证

真实的 Agent 能力不仅表现在最终回答是否正确，还表现在面对不同 observation 时，能否采取合理的后续动作。

通过故障注入、Trace 对照和语料变异，可以更清楚地区分模型自主行为与程序预设行为。

### 5.3 从 AI 生成代码转向 AI 辅助工程闭环

本项目的主要代码由 Codex 辅助实现，但项目质量不能简单依赖 AI 生成结果。

在协作过程中，我更加重视明确技术边界、审查设计取舍、制定可执行验收标准，以及根据真实运行结果确定修复方向。

AI 工具提高了工程实现和测试构建效率，而业务判断、技术约束与交付质量仍需要明确的人工责任边界。

这也使我认识到，在 AI 辅助开发模式下，**提出正确的问题、定义可靠的验证方式，以及识别 AI 生成结果的局限性，与编码实现本身同样重要。**

## 6. 技术局限与后续演进方向

EvidenceAgent 当前采用有限合成语料、结构化规则元数据和受控 Claims 校验，适用于制度类知识问答，但不将该机制视为开放领域的通用事实验证方案。

系统目前具有以下明确边界：

- 对复杂否定、跨主题约束和开放式自然语言条件的覆盖有限。
- 确定性引用及数值核验不能完全替代语义蕴含验证。
- 模型行为具有非确定性，单次 Live 全通过不代表长期稳定性。
- 当前验证基于 DeepSeek Flash 非思考模式，不代表其他模型及服务商具有相同表现。
- 提示注入防护已有离线覆盖，但不能据此宣称真实模型具备完整的对抗鲁棒性。

围绕这些边界，后续工程演进主要有三个方向：

**第一，建立统计意义上的稳定性评估。**

对相同场景进行多次独立 Live 运行，统计任务完成率、证据校验成功率、错误修正成功率、工具故障恢复率及调用成本。

**第二，扩展复杂知识场景。**

逐步支持更复杂的制度范围、跨文档关联和条件组合，并让规则表达能力与验证测试同步扩展。

**第三，完善跨模型兼容性与安全评估。**

通过不同模型的工具调用测试及真实提示注入对抗测试，分析模型行为差异、错误恢复能力和系统安全边界。

这些方向均基于当前系统已观察到的技术边界，而非将未经验证的能力描述为现有功能。

## 7. 最终总结

EvidenceAgent 的核心成果，不只是实现了一个可以检索企业制度的问答 Agent，而是建立了一套具备**真实动态决策、确定性证据保护、错误反馈修正和完整运行追踪**的工程方案。

项目经历了从离线实现、首次真实模型测试失败，到基于 Trace 定位系统性问题、修订交互契约、补充回归测试并完成 Live 验证的完整迭代过程。

最终，项目在本轮取得 **142 项离线测试通过、14 项真实模型测试通过**的结果，并保存了包含动态决策、校验拒绝、故障恢复和持续失败的真实执行记录。

本次实践带来的最大收获是：

**可靠的 Agent 系统不仅要能够作出决策，更要保证决策有依据、执行有边界、错误可修正、结果可验证。**

相比单纯让 LLM 完成任务，将业务要求转化为明确的系统契约，并通过真实执行证据持续改进，是我认为 Agent 工程开发中更重要、也更具有可迁移性的能力。

完整测试结果和动态决策证据见 `docs/03-evaluation.md`，AI 辅助范围及个人贡献见 `docs/04-ai-usage.md`。
