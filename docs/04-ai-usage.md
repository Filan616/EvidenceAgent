## 个人主导工作与 AI 协作分工

### 1. 个人主导与技术决策

本项目采用“**个人主导需求分析、技术决策与质量把控，AI 辅助工程实现与测试验证**”的协作模式。本人负责明确项目目标、制定技术约束、评审实施方案、确定验收标准，并根据实际测试结果推动方案迭代。

**（1）需求分析与系统架构设计**

围绕企业知识问答场景，确定以真实 LLM 驱动的 ReAct Agent 为核心架构，明确模型决策、工具执行、证据校验与运行时保护之间的职责边界。

在方案评审过程中，重点确认以下技术设计：

- 采用原生 Python Tool Calling 实现动态决策，而非通过固定条件分支模拟 Agent 行为。
- 引入显式冲突元数据，结合适用范围、生效时间和条款覆盖关系进行冲突检测，避免简单按照版本日期判断优先级。
- 引入结构化 Claims 与确定性证据校验，保证最终事实声明具有可追溯的文档依据。
- 区分用户明确约束与模型推断字段，允许模型修正自身解释错误，同时防止擅自修改用户要求。
- 建立执行预算、工具异常反馈和结构化 Trace，兼顾 Agent 自主性与工程可靠性。

上述设计经过多轮方案评审与调整，最终形成实施规范，由 Codex 辅助完成具体代码实现。

**（2）测试策略与验收标准把控**

根据项目业务要求，确定正常问答、文档冲突、资料不足、相似问题、上下文追问和工具失败六类核心验收场景。

进一步要求增加语料变异测试、真实动态决策对照、引用可信性校验和执行边界测试，重点验证系统能否根据实际文档与工具 observation 调整行为。

明确区分离线 Mock 测试与真实模型测试：Mock 仅用于验证执行器和校验逻辑，不能代替真实模型的自主决策证据。要求保留实际运行 Trace 和失败记录，不通过放宽验收标准或预设动作制造通过结果。

**（3）真实测试与问题驱动迭代**

本人完成模型配置，并实际执行首次全量 Live 验证，将测试结果及运行日志提供给 Codex 进行分析。

首次测试结果为 122 passed、5 failed。根据 Codex 对真实 Trace 的根因分析，参与确定修复方向，重点解决：

- scope、conditions、period 和 reference_event 的语义混淆；
- 模型自行添加的错误约束无法修正的问题；
- 校验失败反馈不够明确、导致重复无效提交的问题；
- 工具故障测试存在假通过，以及动态决策对照未正确筛选实际执行动作的问题。

在修复要求中强调保留用户原始约束、允许有依据的模型纠错，并要求将实际失败案例转化为回归测试，而不是简单增加执行轮数或放宽校验条件。

后续代码修复、离线回归及第二轮 Live 测试由 Codex 执行。根据其提供的归档测试报告，修复后取得 142 项离线测试通过、14 项 Live 测试通过的结果，并保留原始失败记录与新生成的执行证据。

### 2. AI 辅助实现范围

Codex 主要承担代码生成、模块实现、合成数据与测试夹具构造、自动化测试编写、运行记录生成、文档维护，以及根据已确认的修复方向修改代码等工作。

本人通过需求约束、技术方案评审、验收要求和测试反馈指导迭代，而非将 AI 生成结果直接视为正确实现。

不将 Codex 编写的代码表述为本人独立手写，也不将其自动化测试行为表述为本人亲自执行。

### 3. 验证结果与个人贡献边界

本项目已形成可执行的 Python Agent、自动化测试、实际 Live Trace 和评估文档。

个人可确认的贡献主要集中在需求定义、关键技术取舍、方案评审、质量要求制定、首次真实模型测试及后续问题修复方向的确认。

完整源代码主要由 Codex 辅助编写，第二轮修复和 Live 测试由 Codex 执行。全部源代码的逐行人工复核及最终实际用时确认尚未完成。上述实现和测试阶段未执行 GitHub 提交；后续按用户授权进行发布，实际结果以远端仓库及最终交付记录为准。

本项目体现的主要个人能力是：**将业务需求转化为工程约束，围绕 Agent 可靠性进行技术决策，通过真实测试发现问题，并借助 AI 工具推动系统持续迭代与验证。**
